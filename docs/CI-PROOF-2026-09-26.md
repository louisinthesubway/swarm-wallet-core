# CI proof, 2026-09-26

What the CI for `swarm-wallet-core` has actually proven, what it has not, and where the
published binaries came from. Written so that the claims here can be re-checked without
re-reading the Actions logs, which expire.

Everything below is taken from run logs, not from memory. Where a thing is **not** proven,
it says so.

### The binaries match today's source, even though they predate it

`native/` has not changed since `8340ab7f10167d6c90453944fa965f1e78d8a2f9`:
`git diff 8340ab7 HEAD -- native/` is empty. Every commit after the published build
(`9fed943`, and `eeacf91` itself) touches only `src/` and `test/`. So the published
addon is the addon for the current `native/` tree; what has moved since is TypeScript,
which ships as source.

### A hash identifies one build, not the source

The same source built on 2026-09-26 in run 36257797986 produced
`057f037e…` (linux), `7b7d4c24…` (win32), `820a1de5…` (darwin) — different bytes for
the same input. The addon is **not** bit-reproducible between runs. A hash here says
"these are the bytes that were published", not "this is what the source compiles to".
Provenance of the *source* is `native/PROVENANCE-FILES.tsv`, checked by
`scripts/check-provenance.mjs`.

## The live mainnet test

This is the test that opens a real wallet against mainnet. It runs inside the Linux
addon job, because attaching it to an artifact is not possible (see blockers below).

Proven on 2026-09-26, run 36261609984:

- a new wallet opens on `swarm-mainnet` against `https://lwd-main.swarm.green:8443`
- the server answers `chain=swarm-mainnet height=368 branch=37a5165b`
- the wallet syncs and reports an empty balance

Not proven, and the test now says so explicitly rather than asserting otherwise:

- **the indexer does not report a genesis hash.** `info_server` carries no genesis
  field, so `ServerInfo.genesisHash` is `null` and `genesisVerified` is always `false`.
  The chain is identified by the label the server returns plus the genesis the addon was
  given, not by the server confirming the genesis back. The live test asserts this
  limitation, so the day the addon grows the field, the test fails and says so.
  This is an owner/upstream item, not a defect in this package.

### The bug the live run caught that 104 local tests did not

Run 36261609984's live test failed on `receive address: undefined`. The wallet was fine;
the reader was wrong. `get_unified_addresses` and `get_transparent_addresses` answer an
array of objects whose address is under **`encoded_address`**:

```
unified:     {account, address_index, encoded_address, has_orchard, has_sapling, has_transparent}
transparent: {account, address_index, scope, encoded_address}
```

This is the addon's own shape — `native/src/lib.rs`, and asserted by the addon's Rust
tests in `native/src/lock_discipline_tests.rs`, which read `parsed[0]["encoded_address"]`
and `scope == "external"`. The reader looked for `address`, matched nothing, and returned
an empty list, so `addresses()` reported a wallet with nowhere to receive.

The local tests passed over it because the fake addon answered bare strings. Fixed in
`9fed943`, which also:

- filters transparent addresses to scope `external`; `internal` is change and `refund`
  is the ZIP 320 ephemeral swap scope, and offering either as "your address" publishes
  the wallet's own bookkeeping;
- throws `malformed-response` when the unified list comes back empty, because every
  wallet has at least one unified address, so an empty list means a shape this version
  cannot read — returning `[]` quietly turns that into a Receive screen saying the
  wallet cannot be paid;
- teaches the fake addon the real shape, including an internal change address that must
  not appear in the list.

106 local tests pass, `tsc` clean. **This fix has not been through CI** — see below.

## Two owner blockers, both GitHub billing

Neither is a code problem and neither can be worked around from inside the repo.

**1. Actions artifact storage quota exhausted** (first seen 17:14 UTC). Job
`addon (darwin-arm64)` of run 36257797986 built and passed every check, then went red
solely on `actions/upload-artifact@v4`:

> Failed to CreateArtifact: Artifact storage quota has been hit. Unable to upload any new artifacts.

Worked around: the upload is `continue-on-error`, the binaries go to a Release instead,
and the live test moved into the Linux job so it needs no artifact.

**2. Actions spending limit / failed payment — now blocking every job** (first seen
18:24 UTC, still true 2026-09-27 00:06 UTC):

> The job was not started because recent account payments have failed or your spending
> limit needs to be increased. Please check the 'Billing & plans' section in your settings.

At 18:24 UTC this killed only the `SHA256SUMS on the release` job of run 36261609984.
By the time `9fed943` was dispatched (run 36281465921) it killed **all** jobs: the run
went red in 8 seconds with nothing started. So:

- `9fed943` (the address fix) is unverified by CI. It passes locally: `tsc` clean,
  106 tests.
- A run that fails this way looks like a red build but is not one. Check the
  annotations before believing a failure.

The owner needs to fix the payment method and raise the Actions spending limit for org
`Swarm-Official`, and free artifact storage. Agents cannot see or change billing.

### A defect this created, found and fixed on 2026-09-27

Because the `SHA256SUMS on the release` job never started while the publish step *did*
run, the release was left in a state where **`SHA256SUMS.txt` did not describe the
binaries next to it**. It still held run 36260939776's values:

```
468705aea7a35fcdc163ac057fc9da01e70f70190eeeb78e8786f224f7d1bc73  native-linux-x64.node   <- stale
f0d93b1468c5726cf3a80df708e095630fb7b6b62a732025e99010063e385c6c  native-win32-x64.node   <- stale
```

while the attached `.node` files were run 36261609984's. A `sha256sum -c SHA256SUMS.txt`
failed on two of three binaries. Anyone verifying the download would have concluded the
binaries were tampered with.

`SHA256SUMS.txt` has been regenerated from the bytes actually attached to the release and
re-uploaded; the per-platform `.sha256` files were already correct and agree with it.

Open item, not fixed here: the workflow can still leave a release in this state, because
publishing the binaries and writing the sums are separate jobs and the second can be
skipped while the first succeeds. The sums should be written by the job that publishes,
or the release should stay a draft until the sums job has run.
